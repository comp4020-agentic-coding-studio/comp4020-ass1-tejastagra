# Process overview

## What I built
The power law allocator, an interactive explainer about venture capital returns. A visitor splits a fixed $10m fund across 15 fictional startups, submits and each draws a simulated return from a fat-tailed distribution. The page shows the fund's overall return, a bubble chart sizing each startup by its result and a short explainer on the distribution. Running it again with a different split gives the same lesson: the result came down to whichever startup hit the tail.

## The moments that mattered

1. **Replacing the agent's sliders despite them passing the spec.** The spec requires an `<input type="range">` per startup and the agent built exactly that, fifteen stacked sliders, all tests passing. I rejected the design anyway: dragging a slider to land on a round figure is imprecise and at the 390px marking viewport the tracks are too short to control reliably. I directed it to use plus/minus steppers in $100k increments, which conflicted with the spec. So I kept both. The range inputs stay in the DOM, hidden and unfocusable, with the steppers driving their values ([`7dffa10`](https://github.com/comp4020-agentic-coding-studio/comp4020-ass1-tejastagra/commit/7dffa10)).

2. **Reversing my own fix once I saw its effect on the argument.** One explainer section compares three strategies against the same draw, one concentrated bet, an even split and the visitor's own, to show they land in a similar range. I asked how "one concentrated bet" was calculated and found it hardcoded to array index 0, so it always used the same company regardless of which startup drew the outlier. My first instruction was to point it at the real outlier. That worked and it made the section worse: betting on the winner with hindsight means that bar dominates every time, contradicting the argument being made. I discarded that fix and moved to a random pick each draw, which better represents betting without knowing the outcome, then rewrote the copy to match. The same commit fixed a second instance elsewhere, a four-bucket chart where one bucket was hardcoded and never moved while the other three tracked its slider. It is now derived as `100 - the other three` ([`b9637e0`](https://github.com/comp4020-agentic-coding-studio/comp4020-ass1-tejastagra/commit/b9637e0)).

3. **Adding the rule to CLAUDE.md, later than I should have.** Both bugs above looked correct on screen and only failed once I asked what the number was meant to represent. My harness had nothing to catch this, so I added a rule: verify what a calculated figure represents before accepting it, rather than confirming only that the chart updated. I should have added this after the first bug rather than the second. In the same pass I added a scope rule, since the agent had twice put in changes I never asked for ([`c73c629`](https://github.com/comp4020-agentic-coding-studio/comp4020-ass1-tejastagra/commit/c73c629), [`da9a98e`](https://github.com/comp4020-agentic-coding-studio/comp4020-ass1-tejastagra/commit/da9a98e)).

4. **Specifying the algorithm rather than sending another screenshot.** Results appear as a cluster of circles, one per startup, sized by return multiple so the outlier is visible at a glance. Laying that out took three attempts: a shelf packer and then a masonry column layout each solved the previous problem and introduced a new one, while I kept sending screenshots describing what looked wrong. On the third failure, circles sitting in vertical lanes with gaps, I concluded the problem was in how I was directing it. I stopped describing the symptom and specified the method: largest circle first, then each subsequent circle at the nearest valid tangent point against the cluster. That resolved it in one iteration ([`0bbacfe`](https://github.com/comp4020-agentic-coding-studio/comp4020-ass1-tejastagra/commit/0bbacfe)).

   The chart then overflowed on an extreme draw, where one startup returns 100x or more. I had already been told this class of bug was fixed once ([`e3545b8`](https://github.com/comp4020-agentic-coding-studio/comp4020-ass1-tejastagra/commit/e3545b8)), so I would not accept another visual check as evidence. Extreme draws are too rare to test by clicking, so I had the tail branch forced in a jsdom script by overriding `Math.random` and reproduced the overflow deliberately at both viewports before any code changed. The fix adds a height-fit pass alongside the existing width fit, with a CSS `max-height` backstop. Re-running the script confirmed the chart stays within its cap, with ordinary draws unaffected ([`7b30cc7`](https://github.com/comp4020-agentic-coding-studio/comp4020-ass1-tejastagra/commit/7b30cc7)).
